## 1. 背景与问题

### 1.1 发现经过

实施 PRD-002 的 Track A（已知项检索）时，BM25 配置在 30 条查询上的 **Recall@50、nDCG@10、MRR、P@5 全部为 0.000**。

对照测试排除了实现缺陷：以游戏名或商店描述作为查询时，目标游戏**每次都排第 1**。BM25 本身工作正常。

### 1.2 根因：两路检索的语料**内容**不同

| | 索引字段 | 含评论 |
|---|---|---|
| FAISS（`build_index.py`） | name · description · genres · tags · Modes · **评论** | ✅ |
| BM25（`recommender.py:_init_bm25()`） | name · description×2 · tags×2 · genres | ❌ |

Track A 的查询是玩家评论——用户视角描述游玩体验的语言。BM25 的语料只有开发商撰写的营销文案与标签，**两者几乎没有词汇重叠**，因此一条都命中不了。

> 这与 PRD-001 §1.2 记录的不对称是**两个不同的问题**：
> 那一个是两侧**覆盖的游戏数量**不同（18,449 vs 39,175），正在修复；
> 本文档记录的是两侧**索引的字段内容**不同，此前未被发现。

### 1.3 对系统的实际影响

用户真实提出的查询大量是体验描述式的——"轻松治愈的游戏"、"不要太肝"、"适合和朋友一起玩"。这类表述来自玩家词汇，而非商店文案。

**在这类查询上，BM25 在 RRF 融合中无法贡献任何有效排名**，融合实际退化为单路向量检索。

这直接削弱 C1（RRF 融合）的实际价值，而 C1 已上线（`94830c3`）并已写入报告章节。

### 1.4 缓存无版本标识

`bm25_cache.pkl` 不包含任何语料标识。语料构造逻辑变更后，启动时仍会**静默加载旧缓存**，改动完全不生效且无任何提示。

这与 PRD-001 §1.1 处理的嵌入前缀问题属于同一类隐患：**配置变了但产物没变，且不报错**。

## 2. 目标与非目标

### 2.1 目标

- **G1** 使 BM25 与 FAISS 索引**相同的文本内容**，恢复 RRF 融合在体验描述式查询上的有效性
- **G2** 为 BM25 缓存增加语料标识，使语料变更后无法静默使用陈旧缓存
- **G3** 使 PRD-002 的 Track A 评测对两路检索公平

### 2.2 非目标

- **N1 不调整现有字段权重**。`description×2`、`tags×2` 的重复加权保持原样。本次仅改变一个变量（是否含评论），以保持消融归因干净。字段权重如需调整，应在有实测证据后另行立项
- **N2 不迁移至 SQLite FTS5**。属 PRD-000 的 E3，独立立项
- **N3 不改变 BM25 的游戏覆盖范围**。保持全量 39,175，理由见 PRD-001 §4.2
- **N4 不改动 FAISS 侧任何内容**

## 3. 需求

| 编号 | 需求 | 理由 |
|---|---|---|
| **R1** | `_init_bm25()` 复用 `build_index.fetch_reviews_for_batch()` 取评论 | 与 FAISS 使用**完全相同**的采样规则，不另立一套 |
| **R2** | 评论按与 `build_document()` 一致的条数与截断长度写入语料 | 同上；不一致等于换一种形式重新引入不对称 |
| **R3** | 差评单独纳入，不与好评混同 | 与 FAISS 侧的 `Criticism:` 分段保持一致 |
| **R4** | 缓存写入语料签名（字段构成 + 采样参数 + 游戏数） | 见 §1.4 |
| **R5** | 加载缓存时校验签名，不符则重建并提示 | 静默使用陈旧缓存是不可接受的失败模式 |
| **R6** | 保持 `description×2`、`tags×2` 权重不变 | 见 N1 |

### 3.1 语料构成（变更后）

```
name
short_description  ×2      （不变）
tags (前 20)       ×2      （不变）
genres                     （不变）
好评 6 条 × 200 字符        ← 新增
差评 3 条 × 150 字符        ← 新增
```

### 3.2 缓存签名

```python
CORPUS_VERSION = 2   # 语料构造逻辑变更时递增

signature = {
    "corpus_version": CORPUS_VERSION,
    "n_games": len(app_ids),
    "doc_positive_reviews": B.DOC_POSITIVE_REVIEWS,
    "doc_negative_reviews": B.DOC_NEGATIVE_REVIEWS,
    "doc_positive_chars": B.DOC_POSITIVE_CHARS,
    "doc_negative_chars": B.DOC_NEGATIVE_CHARS,
}
```

## 4. 设计决策

### 4.1 为何评论文本必须与 FAISS 完全一致

**被否决的方案**：BM25 使用更多、更长的评论。BM25 没有上下文长度限制，理论上文本越多可匹配的词项越多。

**否决理由**：本次变更的目的正是**消除两路语料的差异**。若 BM25 使用不同的评论子集，等于换一种形式重新引入不对称，且使 RRF 融合的差异来源无法归因。复用 `fetch_reviews_for_batch()` 亦保证未来任一侧调整采样规则时两侧自动同步。

### 4.2 为何不同时调整字段权重

**被否决的方案**：既然要重建语料，顺带取消 `×2` 重复加权，或为评论设置权重。

**否决理由**：每文档 token 数将从约 100 增至 335，评论占比显著上升，字段平衡确实发生了变化。但若在同一次变更中同时改动"是否含评论"与"字段权重"，两者的贡献将无法分离。**先只改一个变量**，权重调整留待有实测依据后处理。

### 4.3 为何用签名而非文件时间戳做缓存校验

**被否决的方案**：比较 `bm25_cache.pkl` 与 `recommender.py` 的修改时间。

**否决理由**：时间戳会因无关改动（如注释、格式化）而失效，导致不必要的重建；也会因 `git checkout` 等操作被重置而**漏判**。签名直接描述语料构造的输入，判据与实际语义一致。

### 4.4 为何不趁此机会迁移到 FTS5

FTS5 迁移（E3）会同时改变检索实现与索引存储，与本次的语料变更混淆。且 FTS5 的 `bm25()` 与 `rank_bm25` 的实现细节不同，评分不可直接比较。保持本次变更单一。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 重建期间与 FAISS 争抢 I/O | 拖慢 FAISS 重建 | 实测取评论仅需 4.2 分钟，相对剩余 7.6 小时可忽略 |
| BM25 内存与缓存体积增长 | token/文档 100 → 335 | 缓存预计 17 MB → 约 55 MB；已在 `.gitignore` 中 |
| 评论稀释了名称匹配能力 | 精确标题查询变差 | A5 控制测试把关 |
| 陈旧缓存被静默使用 | 变更不生效且无提示 | R4/R5 签名校验，A2 验证 |

## 7. 成本与回滚

**成本**：语料重建约 5 分钟（取评论 4.2 min + 分词 0.2 min + BM25 构建）。

**回滚**：`CORPUS_VERSION` 改回 1 并还原 `_init_bm25()`，删除 `bm25_cache.pkl` 后重建。BM25 缓存不入版本库，无残留。

---

## 8. 对 PRD-002 的影响

Track A 的 BM25 行在本变更前后的数值将不可比。PRD-002 的执行需在本变更完成后再跑基线。

变更前的 0.000 结果予以保留，作为"语料内容缺失"的实证记录，可写入报告——它以实测方式说明了检索系统中语料对齐的重要性。
