# PRD 索引

本目录记录本项目每一次**改变系统行为或产出物**的变更。

## 什么时候要写 PRD

需要写：

- 改变检索、排序、生成任一环节的**行为**
- 改变**索引内容或构建方式**（会导致需要重建）
- 改变**评测协议**（会导致历史数字不可比）
- 引入新的依赖、模型或外部服务

不需要写：

- 修 bug 且不改变预期行为
- 重构、改注释、补测试
- 文档更新

> 判断标准：**如果这次改动会让"之前测出来的数字"失效，就要写 PRD。**

## 编号与状态

编号 `PRD-NNN`，三位数字，只增不减。废弃的编号不回收。

| 状态 | 含义 |
|---|---|
| `草案` | 还在讨论，方案未定 |
| `待确认` | 方案已定，等待批准 |
| `已批准` | 已批准，尚未开始 |
| `实施中` | 正在执行 |
| `已完成` | 已完成并验收通过 |
| `已废弃` | 被后续 PRD 取代，需注明取代它的编号 |

## 文件命名

```
PRD-001-index-corpus-rebuild.md
PRD-<编号>-<kebab-case 简短标题>.md
```

## 每份 PRD 必须包含

1. **元信息** —— 编号、版本、状态、日期、关联提交
2. **背景与问题** —— 为什么要做，不写解决方案
3. **目标 / 非目标** —— 明确划定范围边界
4. **需求** —— 编号列出，每条附理由
5. **设计决策** —— 含**被否决的方案及否决理由**
6. **验收标准** —— 必须可验证，不能是"效果更好"
7. **风险与应对**
8. **成本与回滚方案**
9. **变更记录** —— 每次修订记录改了什么

> 第 5 条的"被否决方案"最容易被省略，但它是这份文档**几个月后还有价值**的唯一原因——它记录了当时为什么**没有**选另一条路。

## 文档层级

```
OPTIMIZED_DESIGN.md          范围与技术依据的唯一来源
        │                    （为什么这么做、原理是什么）
        ▼
PRD-000 总体方案              执行台账：做哪些、现在到哪了
        │
        ├──▶ PRD-001 …        一事一档：具体怎么做、怎么验收
        └──▶ PRD-002 …
```

**新增变更时**：先确认 `OPTIMIZED_DESIGN.md` 中是否已有对应方案。
若有，在 PRD-000 的变更清单中登记编号并新建子 PRD；
若无，**先更新 `OPTIMIZED_DESIGN.md`**，再走上述流程——避免两处论述分叉。
