## 1. 背景与问题

### 1.1 排序层目前没有语义判断

课程评审对本项目类别的批评中最重的一条：

> "In several cases, `rank_candidates()` only truncated the top-N retrieval results. **That is not really RE-ranking.**"

当前 `rank_candidates()` 已不再是简单截断，它做四件事：

1. 混合相关性与质量分（`0.40 × relevance + 0.60 × quality`）
2. 硬约束过滤（价格、平台）
3. 偏好加分（便宜、新、复古）
4. 多样性约束

**但其中的"相关性"仍然来自融合排名，而非对查询与候选的语义判断。** RRF 只知道"两路检索都觉得它靠前"，它没有读过查询和文档的对应关系。

对多子句查询尤其明显：报告 §3.3.3 记录的第 2 轮失败——"intellectually stimulating **and** require some gaming experience"，系统只匹配了前半句。单个查询向量被最显著的词主导，而融合排名无法纠正这一点。

### 1.2 原实现选错了工具

`_rank_with_llm()` 完整实现了生成式 LLM 重排（JSON 输出、评分解析、评论证据），因性能被关闭。其 docstring 记录：

> CPU 上每次查询多花约 550 秒，长 prompt 的 prefill 占绝大部分。

**根因不是"重排本身昂贵"，而是工具错配：**

| | 生成式 LLM（`phi4-mini`） | Cross-encoder |
|---|---|---|
| 参数量 | 38 亿 | 2,200 万 ~ 5.7 亿（取决于选型） |
| 输入形态 | 50 个候选拼成一个超长 prompt | 50 个短句子对，可批量并行 |
| 输出方式 | **逐 token 自回归解码** | **一次前向传播输出一个标量** |
| 实测/预期耗时 | ~550 秒 | 待测（§5 第 0 步） |

**生成式模型必须逐字输出**，这是它慢的根本原因。重排只需要一个分数，不需要任何文字。

### 1.3 依赖可行性（已实测）

| 组件 | macOS x86_64 / Python 3.13 | 结论 |
|---|---|---|
| `torch` | **无可用 wheel**（仅 `macosx_14_0_arm64`、Linux、Windows） | ❌ `sentence-transformers` 路线不可行 |
| `onnxruntime` | 1.23.2 可安装 | ✅ |
| `tokenizers` / `transformers` | 可安装 | ✅ |
| `huggingface_hub` | 可安装 | ✅ |

**ONNX Runtime 是唯一可行路径。** 模型需使用**已预导出为 ONNX** 的版本——本机无法自行导出（导出工具链依赖 torch）。

## 2. 目标与非目标

### 2.1 目标

- **G1** 在排序层引入真正的语义重排，使相关性判断建立在查询与候选的联合编码之上
- **G2** 单次查询新增延迟控制在可接受范围内（§4.4 给出预算）
- **G3** 重新标定质量权重——相关性信号更换后，原标定值不再成立
- **G4** 以检索评测与端到端评测共同验收，不以任一单方为准

### 2.2 非目标

- **N1 不改动召回与融合**。重排不改变候选集合，Recall@50 必须保持不变
- **N2 不更换生成模型**
- **N3 不移除现有排序步骤**。硬过滤、偏好加分、多样性约束保留，仅替换相关性信号来源
- **N4 不自行导出 ONNX 模型**。本机无 torch，只使用已预导出的模型
- **N5 不追求最强模型**。CPU 推理下，延迟与质量的平衡优先于绝对精度

## 3. 方案

### 3.1 位置：融合之后，混合之前

```
39,176 款游戏
   │
   ├─ FAISS 向量检索（100） ┐
   │                        ├─ RRF 融合 ──→ 50 个候选
   ├─ BM25 词法检索（100） ┘
   │
   ▼
50 个候选
   │
   ▼  ← Cross-encoder：逐个计算 (query, doc) 相关性
   │
   ▼
混合：w_rel × ce_score + w_qual × quality
   │
   ▼
硬过滤 → 偏好加分 → 多样性约束 → 前 10
   │
   ▼
生成层选 5
```

**为什么必须在融合之后**：Cross-encoder 无法预计算——换个查询就要重算全部。39,000 次前向传播不可行，50 次可行。这是召回—重排两阶段架构的根本原因。

**Cross-encoder 救不回融合漏掉的条目。** 正确答案未进前 50 时，重排再准也无用。因此：

| 阶段 | 关注指标 | 性质 |
|---|---|---|
| 召回 + 融合 | **Recall@50** | 整个漏斗的**上界** |
| 重排 | **nDCG@10 / MRR** | 候选池固定，仅关心顺序 |

### 3.2 分数如何接入

Cross-encoder 输出相关性分数，**替换**现有的 `relevance` 项：

```python
# 现状
relevance = rec.raw["_rrf"] / max_rrf

# 变更后
relevance = ce_scores[i]        # cross-encoder 输出，经 sigmoid 归一化到 [0,1]
```

后续 `_score = w_rel × relevance + w_qual × quality` 的结构不变。

### 3.3 送入 cross-encoder 的文本

候选侧文本需要在信息量与长度间取舍——cross-encoder 有输入长度上限，且长度直接影响延迟。

**方案**：`名称 + 标签（前 8）+ Modes + 商店描述（前 200 字符）`

不含评论。理由见 §4.5。

## 4. 设计决策

### 4.1 为何用 cross-encoder 而非继续用生成式 LLM

**被否决的方案**：保留 `_rank_with_llm()`，通过缩短 prompt（只给标签、只重排前 20）把 550 秒压到可接受范围。

**否决理由**：这是在缓解症状。生成式模型的成本来自**自回归解码**——它必须逐 token 产生输出。而重排任务的输出是一个标量，不需要任何生成。Cross-encoder 一次前向传播即可，架构上就没有这项开销。

缩短 prompt 同时会削弱判断依据，属于用质量换速度；换工具则两者都不牺牲。

### 4.2 为何替换相关性项而非再做一次融合

**被否决的方案**：把 cross-encoder 分数与 RRF 分数再做一次 RRF 融合。

**否决理由**：Cross-encoder 的相关性判断严格优于融合排名——RRF 只知道"两路都觉得它靠前"，cross-encoder 实际读取了查询与文档的对应关系。保留 RRF 分数只会稀释更强的信号。

工业界确有二次融合的做法，但那是在 cross-encoder 可靠性不足时的保险策略，不应作为默认选择。若第 0 步验证显示模型判断不稳定，可回退至此方案，届时另行记录。

### 4.3 为何质量权重必须重新标定

现行 `0.40 / 0.60` 是针对**归一化 RRF 排名**标定的（[PRD-006](PRD-006-quality-weight-recalibration.md) §2）。

Cross-encoder 分数的**分布形态完全不同**：RRF 归一化后在 [0,1] 上近似均匀衰减，而 cross-encoder 的 sigmoid 输出通常高度集中在两端。用旧权重混合等于把一个未经标定的信号塞进已标定的公式。

**必须重跑 §2 的扫描实验。**

> 这是从 PRD-006 学到的教训：`0.25` 那个取值是**凭论证设定**而非标定的，而论证含有一个未经验证的隐含假设。任何改变信号分布的变更都会使既有标定失效。

### 4.4 延迟预算

当前单次查询中位 **106 秒**（含查询扩展、检索、结构化生成）。`LLM_TIMEOUT` 为 360 秒。

**预算：cross-encoder 新增延迟 ≤ 15 秒（占现有耗时 14%）。**

超出则需缩减重排范围（如只重排前 20）或改用更小的模型，并在第 0 步记录取舍。

### 4.5 为何送入 cross-encoder 的文本不含评论

**被否决的方案**：把评论摘要也送进去，与索引文档保持一致。

**否决理由**：

1. **长度直接换延迟**。索引文档均长 2,110 字符，其中评论占 66%。带评论会使输入长度增至约 3 倍，延迟按比例上升
2. **cross-encoder 有输入长度上限**，超出即截断——而截断点通常落在评论中间，等于送入一段无意义的残句
3. 评论的价值主要体现在**召回**阶段（PRD-003 实测：BM25 语料纳入评论使 Recall@50 由 0.000 升至 0.133）；到重排阶段，候选已经相关，需要判断的是**哪一个更贴合查询的具体措辞**，商店描述与标签的信息密度更高

若第 0 步显示延迟有富余，可作为变体测试。

### 4.6 模型选型的取舍

CPU 推理下参数量直接决定延迟。第 0 步将实测以下候选：

| 模型 | 参数量 | 预期特点 |
|---|---|---|
| `ms-marco-MiniLM-L-6-v2` | ~2,200 万 | 经典快速重排器，6 层；英文，速度最优 |
| `bge-reranker-base` | ~2.78 亿 | 更强，约 10 倍参数量 |

**N5 已声明不追求最强模型。** 若小模型在 Track B 上已能取得可辨识改善且延迟远低于预算，优先采用小模型——延迟每增加一秒都是真实的用户成本，而评测样本量（50 条）本就难以分辨小幅质量差异。

- [x] **A1** 第 0 步：ONNX 模型可加载，50 对推理延迟 ≤ 15 秒
- [ ] **A2** Track A 的 Recall@50 与变更前**完全相同**（重排不改变候选集合）
- [ ] **A3** Track B 的 nDCG@10 相对 `full` 配置（0.469）有可辨识提升
- [ ] **A4** 质量权重经重新扫描标定，取值依据记入代码注释
- [ ] **A5** 单次查询延迟中位数增幅 ≤ 15 秒
- [ ] **A6** 单元测试全部通过；新增 `_rerank_cross_encoder()` 的构造测试（模型不可用时降级、空候选、分数全相同）
- [ ] **A7** 模型不可用时降级为 RRF 排名，且在 `meta` 中标明（不得静默降级）
- [ ] **A8** judge 三次评分完成，修订系统均值高于 PRD-006 记录的 62.5
- [ ] **A9** 与原系统 71.2 的差距缩小，或缩至评委批次间漂移（2.5 分）以内

> **A8 / A9 可能不达成。** 若端到端未回升而 Track B 有提升，说明改善集中在检索真值能捕捉的维度上，而端到端差距另有来源——依 [PRD-006](PRD-006-quality-weight-recalibration.md) §10.5 的先例，**不得反复调参追分**，应回到根因分析。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| ONNX 模型加载失败或无预导出版本 | 方案不可行 | 第 0a 步先验证；失败则终止并记录 |
| 延迟超出 15 秒预算 | 交互体验恶化 | 缩减重排范围 → 换更小模型 → 终止 |
| 小模型质量判断不如 RRF 排名 | 得不偿失 | A3 以 Track B 把关；不达标则回退 |
| 权重沿用旧值导致混合失衡 | 改善被抵消 | §4.3 强制重新标定 |
| 模型加载失败时静默降级 | 变更不生效且无提示 | A7 要求在 `meta` 中标明，与 `generation_mode` 同一原则 |
| 新增网络依赖（模型下载） | 破坏"解压即可运行" | 模型文件纳入版本库或提供下载脚本；README 说明 |
