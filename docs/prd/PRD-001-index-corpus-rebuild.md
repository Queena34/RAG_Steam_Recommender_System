## 1. 背景与问题

当前向量索引由 `build_index.py` 于 2026-05 构建，共 18,449 个向量。在为优化工作做代码审查时，发现该索引的构建方式存在四个问题。它们互相独立，但**都只能通过重建索引来修复**，因此合并为一次变更。

### 1.1 嵌入模型的任务前缀缺失

`nomic-embed-text` 是**非对称检索模型**：它要求输入带任务前缀，以区分"被索引的文档"和"用户查询"。文档侧应为 `search_document: `，查询侧应为 `search_query: `。

建库和查询两侧**都没有添加**。这不会导致报错，因此长期未被发现，但会损失检索质量——模型无法区分一段长商店页面和一句简短查询，而检索恰恰要求二者匹配。

### 1.2 向量与词法语料范围不一致

| 索引 | 构建位置 | 过滤条件 | 规模 |
|---|---|---|---|
| FAISS | `build_index.py` | `positive > 100` | 18,449 |
| BM25 | `recommender.py:_init_bm25()` | 无 | 39,175 |

两者由不同代码路径构建，条件不同。此前 BM25 仅作为降级备份、**实际从未执行**，因此该不一致未暴露；引入 RRF 融合、两路并行后才成为问题。

在 RRF 下这个不一致不是中性的：**仅出现在单一排名中的条目无法获得共识加成**，其融合得分上限约为双路命中条目的一半（`1/61` vs `1/61 + 1/62`）。

进一步核查发现，被 `positive > 100` 排除的 20,726 个游戏分为两类性质完全不同的条目：

- **12,244 个**：`positive` 在 11–100，是评论数少但正常的小众游戏（抽样：`Psyvariar Delta +47/-5`、`Quantum Odyssey +40/-2`）
- **8,373 个**：`positive` 与 `negative` **同时为 0**，即评分元数据缺失。这些条目在 `reviews` 表中确有评论记录，因此并非"全部差评"，而是字段未采集

即：`positive > 100` 实际是在按**数据完整性**过滤，而非按游戏质量过滤。

### 1.3 评论采样选中了信息密度最低的文本

评论占文档字符数的 **66%**（实测：文档均长 1,522，评论 1,010，描述仅 201），是嵌入质量的主导因素。当前采样存在三重缺陷：

1. `ORDER BY LENGTH(review) DESC` 优先取最长评论，而超过 2,000 字符的评论仅占 3.6%——这一小撮长篇评论被排在最前
2. `build_document()` 实际只使用前 5 条、每条截断至 200 字符。**最终进入嵌入的是"最长 5 篇评论各自的开头 200 字符"**，而长评论开头通常是铺垫或玩梗
3. `votes_up` 字段（社区认可度）完全未使用。实测 24% 的评论获得 ≥3 个赞，是比长度可靠得多的质量信号

### 1.4 差评被完全丢弃

`WHERE voted_up = 1` 排除了全部差评。差评占全部评论的 20.4%，每个游戏通常有数十条可用。

"太难""太肝""bug 多"这类信息**只存在于差评中**。报告 §3.3 记录的失败案例中，"不要太难的游戏"这类否定型查询无法得到支持，与此直接相关。

### 1.5 游戏模式信息未进入语料

`categories_json` 含 `Multi-player`（25.5%）、`Co-op`（14.6%）、`PvP`（14.1%）等字段，但 `build_document()` 从未读取该列。

**这是报告 §3.3.3 记录的第 3 轮失败的直接原因**：查询要求 "play with friends"，系统推荐了单人游戏 *We Who Are About To Die*——向量检索在语料中根本看不到游戏模式信息。

## 2. 目标与非目标

### 2.1 目标

- **G1** 修复嵌入前缀缺失，并在机制上排除双侧前缀不一致的可能
- **G2** 缩小向量与词法语料的范围差距，提升 RRF 融合的公平性
- **G3** 提升评论采样质量，使其反映玩家实际体验而非文本长度
- **G4** 将游戏模式（单人/多人/合作）纳入语料，支撑此类约束的语义检索
- **G5** 保留旧索引，使"前缀 + 覆盖率"的贡献可在消融实验中被单独量化

### 2.2 非目标

明确**不在**本次范围内，避免范围蔓延：

- **N1 不更换嵌入模型**。更换模型会与本次的语料变更混淆，导致消融表无法归因
- **N2 不做分块嵌入**（一个游戏拆多个向量）。这会将 `app_ids` 从游戏级改为分块级，检索需增加去重逻辑，构建时间翻倍
- **N3 不改变 FAISS 索引类型**。`IndexFlatIP` 在 3 万条规模下精确且足够快
- **N4 不改动排序与生成环节**
- **N5 不改动 `recommender.py:_fetch_game_details()` 的评论采样**。该处仅用于 LLM 生成推荐语，与索引无关，不需要重建即可修改

## 3. 需求

| 编号 | 需求 | 理由 |
|---|---|---|
| **R1** | 文档侧添加 `search_document: ` 前缀 | 模型的非对称检索要求 |
| **R2** | 前缀配置写入 `meta.json` 的 `doc_prefix` / `query_prefix` | 查询侧读取配置而非硬编码，旧索引（无该字段）自动按无前缀查询 |
| **R3** | 续建时校验 `doc_prefix` 一致，不符则拒绝 | 前缀混建会在一个索引内混合两种嵌入空间，且不会报错 |
| **R4** | 覆盖阈值改为 `positive > 10`（30,693 个） | 排除评分元数据缺失的条目，而非按人气过滤 |
| **R5** | 评论按 `votes_up DESC` 排序，长度作次级排序 | 社区认可度优于文本长度 |
| **R6** | 评论长度窗口限制在 100–1500 字符 | 过短无信息量，过长为评论散文 |
| **R7** | 好评差评**分流采样**，各自独立排名 | 好评多的游戏仍应贡献批评，差评多的游戏仍应贡献肯定 |
| **R8** | 文档中差评单独标注为 `Criticism:` | 使模型知晓该段为负面评价，而非混入正面描述 |
| **R9** | 新增 `Modes:` 行，白名单过滤 `categories_json` | 该字段混有无障碍与硬件说明，"Custom Volume Controls" 对所有游戏都成立，属噪声 |
| **R10** | 重建前备份现有索引至 `vector_index_baseline_18k/` | 消融实验对照行的唯一来源 |

### 3.1 参数取值

```python
MIN_POSITIVE          = 10      # 覆盖阈值
MAX_POSITIVE_REVIEWS  = 15      # SQL 取样上限
MAX_NEGATIVE_REVIEWS  = 5
REVIEW_MIN_CHARS      = 100
REVIEW_MAX_CHARS      = 1500
DOC_POSITIVE_REVIEWS  = 6       # 实际进入文档
DOC_NEGATIVE_REVIEWS  = 3
DOC_POSITIVE_CHARS    = 200
DOC_NEGATIVE_CHARS    = 150
```

`CATEGORY_WHITELIST` 共 12 项：`Single-player`、`Multi-player`、`Co-op`、`Online Co-op`、`LAN Co-op`、`Shared/Split Screen Co-op`、`PvP`、`Online PvP`、`LAN PvP`、`Shared/Split Screen PvP`、`MMO`、`Cross-Platform Multiplayer`。

### 3.2 目标文档格式

```
search_document: Game: Towers Deck
Description: A combination of Tower Defense and Rogue-like deckbuilding...
Genres: Indie, Strategy
Tags: Tower Defense, Isometric, Roguelike Deckbuilder, ...   （按票数前 15）
Modes: Single-player
Release: Feb 1, 2023
Rating: 75% positive (40 reviews)
Player reviews: <6 条，各 200 字符>
Criticism: <3 条，各 150 字符>
```

## 4. 设计决策

### 4.1 覆盖阈值为何取 10

| 方案 | 规模 | 耗时 | 结论 |
|---|---|---|---|
| 保持 `> 100` | 18,449 | 约 6.6 h | ❌ 边际成本不划算：仅修前缀就要 6.6 h，不如顺带扩覆盖 |
| **`> 10`** | **30,693** | **约 10.1 h** | ✅ **采用** |
| 无过滤 | 39,175 | 约 12.8 h | ❌ 多出的 8,373 个评分元数据缺失，Wilson 质量分恒为 0.0 |

选择 `> 10` 的核心理由：多出的 12,244 个是正常小众游戏，正是本系统相对通用大模型的差异化优势所在（详见 `OPTIMIZED_DESIGN.md` §11.3）。而排除元数据缺失条目在报告中是一条干净的技术理由，优于武断的人气阈值。

### 4.2 BM25 为何保持全量、不与向量对齐

**被否决的方案**：将 BM25 也限制为 `positive > 10`，使两侧完全对称。

**否决理由**：

1. BM25 构建不调用嵌入模型，多索引 8 千条几乎零成本，没有成本压力去过滤
2. 它是**精确标题匹配的唯一途径**。用户搜索冷门游戏的确切名称时，向量检索会漂移到同类游戏；若从 BM25 中也移除，该游戏将彻底不可达

**代价需在报告中明确说明**：仅存在于单一语料的条目无法获得 RRF 共识加成，融合得分上限约为双路命中条目的一半。本次变更将该差距从 20,726 缩小至 8,482。

### 4.3 为何接受耗时从 6.3 增至 10.1 小时

**被否决的方案**：将文档内好评从 6 条减至 4 条，可节省约 2 小时。

**否决理由**：评论占文档 66%，是嵌入质量的主导变量。而两个方案**都在同一夜内完成**（18:00 启动分别为次日 00:20 与 04:10），墙钟时间上的实际差异为零。

### 4.4 为何不做分块嵌入

`OPTIMIZED_DESIGN.md` §11.1 曾将分块列为改善语料信息天花板的手段。本次不做，理由：

- `meta.json` 的 `app_ids` 需从游戏级改为分块级，检索后要按游戏去重，`_rrf_fuse()` 的语义也随之改变
- 构建时间随分块数线性增长
- 属于架构变更，应独立立项而非搭车

列为 future work。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 重建中途进程被杀 | 损失部分进度 | 每 100 个游戏写检查点，重跑自动续建 |
| 检查点写到一半崩溃 | 索引与映射错位，**静默返回错误游戏** | 已实现原子写 + `ntotal == len(app_ids)` 校验（`6c62987`） |
| Ollama 服务中断 | 该批次报错，计入 `errors` | 构建脚本跳过并继续；结束时检查 `Errors` 计数 |
| 新索引质量反而下降 | 需回退 | `vector_index_baseline_18k/` 可直接换回 |
| 重建期间启动 Flask | 读到写了一半的索引 | 重建期间禁止启动应用；一致性校验也会拦截 |
| 索引体积 94 MB | 接近 GitHub 100 MB 硬上限 | 见 §7.2，需单独决策 |

## 7. 成本与回滚

### 7.1 成本

| 项 | 数值 |
|---|---|
| 构建耗时 | 约 10.1 小时（实测 0.85 游戏/秒） |
| 索引体积 | 约 94 MB（30,693 × 768 × 4 字节） |
| 磁盘占用 | 新索引 94 MB + 备份 54 MB |
| 不可用窗口 | 重建期间应用不可启动 |

### 7.2 遗留决策

新索引约 94 MB，接近 GitHub 单文件 100 MB 硬上限（50 MB 起告警）。提交方式需在验收后另行决定：直接提交 / Git LFS / 不提交而要求使用者自建。**本 PRD 不涵盖此项。**

### 7.3 回滚

```bash
rm -rf vector_index
cp -R vector_index_baseline_18k vector_index
```

旧索引无 `query_prefix` 字段，`recommender.py` 读取后为空字符串，自动退回无前缀查询模式，无需改代码。
