## 1. 背景与问题

### 1.1 已完成的改动无法用现有指标体现

C3（结构化生成）消除了实体幻觉，其收益集中在报告评分卡的"可验证性"维度（30 分）。
[PRD-002](PRD-002-evaluation-framework.md) 的检索评测**测不到这一层**——它评的是检索与排序，不含生成。

第 4 轮"免费合作游戏"因推荐了 *Wolvesville*（Steam 上不存在）与 *Sonder*（无法验证）而失分，
该轮得 50 分。**只有 judge 协议能测出这项改动的效果。**

### 1.2 基线分数与新分数不可比

报告 Table 14 的分数来自**单次评分**。LLM 评委不是确定性的，单次结果无法区分
"系统差异"与"评分波动"。若用新的多次均值去比旧的单次值，等于把系统变化与测量方式变化混在一起。

### 1.3 评分者独立性存在被破坏的风险

报告 §3.3.1 明确声明使用第三方 LLM 作为**独立**评委，理由是"避免自评固有的主观性"。

本轮改动由 AI 助手实施。**若由同一方评分，该独立性声明即不成立**，报告中的方法论主张将变为不实陈述。

## 2. 目标与非目标

### 2.1 目标

- **G1** 在同一协议下取得修订系统、原系统、ChatGPT 三方的可比分数
- **G2** 通过多次评分量化评委噪声，使"改进"可与噪声区分
- **G3** 维持评分者独立性，使报告 §3.3.1 的声明继续成立
- **G4** 产出可填入 `section_post_optimization_eval.tex` 的数值

### 2.2 非目标

- **N1 不扩充 prompt 数量**。扩到 20–25 条需要为新 prompt 补 ChatGPT 回答，否则三方不可比。样本量问题在本 PRD 之外
- **N2 不修改评分卡维度与配分**。改动维度会使新旧分数再次不可比
- **N3 不由实施方评分**。见 §1.3

## 3. 需求

| 编号 | 需求 | 理由 |
|---|---|---|
| **R1** | 用修订系统跑原 5 条 prompt，每条 3 次 | 生成非确定性，单次结果不足以代表系统 |
| **R2** | 记录 PRD-004 的 telemetry（生成模式、拒绝数、证据支持率） | 与 judge 分数并列报告，说明分数从何而来 |
| **R3** | 三方结果匿名化，**每轮独立打乱**标签 | 固定顺序会让评委从位置推断来源 |
| **R4** | 原系统与 ChatGPT 的记录输出**一并重新评分** | 见 §1.2 |
| **R5** | 评分执行 3 次，分别在独立会话中 | 量化评委噪声 |
| **R6** | 聚合时报告均值与跨次标准差 | 差值小于噪声者不得称为改进 |
| **R7** | 标签映射表与评分包分离存放 | 评分包交付时不得附带答案 |

## 4. 设计决策

### 4.1 为何必须重新评分基线，而非沿用 Table 14

**被否决的方案**：只评修订系统，与 Table 14 的已有分数对比。

**否决理由**：那些分数是单次评分。多次均值与单次值之差包含两个来源——系统改动与测量方式改动——无法分离。
重新评分的成本仅为评分包中多两组结果，而收益是结论可归因。

### 4.2 为何是 3 次而非更多

3 次足以估计标准差量级并识别异常值，且评分工作量可控。更多次数的边际收益递减，
而每次都需要人工在独立会话中完成。

### 4.3 为何不由实施方评分

见 §1.3。这不是效率问题而是效力问题：**自评的分数无法支撑报告已作出的独立性声明**。

补充说明：即便实施方"努力保持客观"也不解决问题。协议的价值在于**结构上排除**利益关联，
而非依赖评分者的自律——这与 C3 中"机制保证优于概率改善"是同一条原则。

## 9. 采集阶段的发现

### 9.1 受约束解码撞上了既有超时设置（已修复）

首轮采集 15 次中 **3 次降级为 `fallback-ranking`，全部因超时**，而非 schema 失败。

| 轮 | 延迟区间 |
|---|---|
| R1 模糊 | 113–165s |
| R2 详细 | 103–125s |
| R3 否定 | 113–171s |
| R4 硬约束 | 149–186s |
| **R5 类比** | **182–269s** |

R5 三次全部超时。原因是该 prompt 的查询扩展输出异常长（一次生成 30+ 个词组），
拖慢了其后每一级。`LLM_TIMEOUT` 由 150s 提至 360s 后重跑，R5 恢复为 2 次 structured + 1 次 partial。

**这是 PRD-004 未预见的副作用**：其风险表列出了"受约束解码显著增加延迟"，
但未预料到它会直接超出为自由文本生成设定的阈值。用户在真实使用中同样会遇到，
属于应写入报告的工程发现。

### 9.2 标识符校验在真实查询上触发

首轮采集拦下 **2 个**候选集外的 app_id，R5 重跑再拦下 **1 个**。

这比第 0 步 spike 的"0 个"更有价值——**它证明模型确实会编造，而校验确实拦住了**。
PRD-004 §11.2 区分的"A7 是结果、A2 才是保证"，在此得到实证。

证据支持率：首轮 0.98，R5 重跑 0.92。

### 9.3 报告对第 4 轮失败的归因需要修正

原报告 §3.3.3 称第 4 轮推荐了 *Wolvesville*（"not available on Steam"）
与 *Sonder*（"could not be verified as an existing free co-op game"），并归因为事实性幻觉。

数据库核查结果：

| 游戏 | appid | 价格 | 评价 | 类目 |
|---|---|---|---|---|
| Sonder | 2692570 | 免费 | +468 / −51 | Multi-player, **Co-op**, Online Co-op, Shared/Split Screen Co-op |
| Wolvesville | 2502760 | 免费 | +825 / −188 | Multi-player, Cross-Platform Multiplayer |

**两者都真实存在于 Steam 与本项目快照中。** Sonder 更是完全符合查询——免费、合作、多人、90% 好评。

即：第 4 轮失去的"可验证性"分数**并非源于系统编造，而是源于评委无法验证冷门条目**。
两者分别只有 468 与 825 条好评，相对动辄数十万好评的知名游戏属于长尾。

这印证了 `OPTIMIZED_DESIGN.md` §11.3 的论证：**judge 对知名游戏存在确认偏误**，
符合条件但冷门的推荐会因评委缺乏判断依据而被判低分。

**对 C3 预估的影响**：`section_expected_gains.tex` 将第 4 轮的 +37 分归因于 C3 的标识符校验。
该归因需要修正——校验确实使"推荐库外游戏"成为不可能，但**第 4 轮的失分本就不是这个原因造成的**，
故该轮的预估收益偏高。

## 10. 评分结果

完整数据见 [`eval/judge/judge_results.md`](../../eval/judge/judge_results.md)。

| 轮次 | 原系统 | 修订系统 | ChatGPT |
|---|---|---|---|
| R1 模糊 | 83.3 ± 4.5 | 74.3 ± 2.9 | 96.0 ± 0.0 |
| R2 详细 | 73.0 ± 1.7 | **45.3 ± 9.3** | 99.0 ± 0.0 |
| R3 否定 | 61.0 ± 6.6 | **67.7 ± 5.5** | 98.7 ± 0.6 |
| R4 硬约束 | 68.0 ± 2.0 | **57.7 ± 5.9** | 94.7 ± 0.6 |
| R5 类比 | 58.0 ± 3.5 | 58.7 ± 4.0 | 95.0 ± 1.0 |
| **均值** | **68.7** | **60.7** | **96.7** |

评委噪声（单轮跨次标准差中位数）：**2.9 分**。

### 10.1 修订系统退步 8 分

R2（−27.7）与 R4（−10.3）的差值远超噪声，是真实退步。仅 R3（+6.7）改善。

### 10.2 重评基线是发现这一点的前提

原系统发表分数为 **60.2**（单次评分），三次重评为 **68.7**，相差 8.5 分。

若采用 §4.1 中被否决的方案——直接以新分数对比 Table 14——将得出"60.7 vs 60.2，基本持平"，
而与同协议基线相比实为退步 8 分。**§4.1 的决策在此得到验证。**

### 10.3 根因：排序权重，而非检索改动

推荐游戏的好评数中位数：

| 轮次 | 原系统 | 修订系统 | ChatGPT |
|---|---|---|---|
| R1 | 10,173 | **85** | 26,639 |
| R2 | 6,518 | **60** | 28,093 |
| R3 | 30,411 | 25,297 | 80,268 |
| R4 | 1,095 | 468 | 209,822 |
| R5 | 23,445 | **596** | 5,218 |
| **全部** | **8,935** | **468** | **37,721** |

修订系统推荐条目的评论数约为原系统的 **1/19**。得分最低的 R2 中位仅 **60** 条好评。

机制链条：

1. C7 将索引阈值由 `positive > 100` 降至 `> 10`，纳入 12,244 个长尾条目
2. C5 的质量分权重为 **0.25**，相关性为 **0.75**
3. 一个仅 60 条好评但语义高度匹配的条目，0.25 的质量惩罚**不足以抵消** 0.75 的相关性优势

### 10.4 检索评测为何测不出这个问题

Track A 的真值是"是否找回特定游戏"，Track B 的真值是"标签是否匹配"。
**两者都不衡量一个游戏是否值得被推荐。**

C1 与 C5 在检索层面分别取得 3.5σ 与 2.9–3.6σ 的显著改善，端到端却退步——
这不是矛盾，而是说明**检索指标与推荐价值不是同一件事**，两层评测缺一不可。

### 10.5 冷门 ≠ 差，但也不是没有代价

两种效应同时存在：

- **评委知名度偏误**：R4 的 Sonder 免费、有 Co-op 类目、90% 好评，**完全符合查询**，
  但评委难以验证。这属于 `OPTIMIZED_DESIGN.md` §11.3 论证的偏误
- **推荐价值确实较低**：R2 中位 60 条好评的条目，面对"需要游戏经验、智力挑战"这类
  依赖口碑背书的需求，**用户无从判断是否值得投入时间**

本轮以第二种效应为主。

### 10.6 后续

本问题可修，且不需回滚 C7——`QUALITY_WEIGHT` 取值需要重新标定。
诊断实验：扫描该权重，观察推荐条目好评数中位数与 Track B 的 nDCG 如何共同变化。
不涉及索引重建。
