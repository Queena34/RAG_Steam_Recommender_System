## 1. 背景与问题

### 1.1 用正则从自由文本中还原推荐结果

`_generate_with_llm()` 让模型输出一段自然语言，再用三个正则抠出游戏名：

```python
patterns = [
    r'^\d+\.\s+([^[\n\-–]+)',
    r'^([^[\n\-–]+)\s*[\-–]',
    r'^([^[\n]+)\[',
]
```

随后在 `search()` 中用前缀模糊匹配反查记录：

```python
if name.startswith(sel) or sel.startswith(name):
```

三层脆弱性：

1. **格式漂移即失配**。模型少写一个 `[`、将 `–` 写成 `—`、改用无序列表，正则全部失效
2. **失配后静默降级**。`selected_names` 为空时回退为"按分数取前 5" + 模板文本，用户与开发者均无提示
3. **前缀匹配可能命中错误条目**。`"Half-Life"` 会匹配到 `"Half-Life 2"`

这些失败**均不产生任何错误信号**，最终呈现的推荐语与结果卡片可能并不对应。

### 1.2 实体幻觉已在评测中发生

报告 §3.3.3 记录，第 4 轮"免费合作游戏"推荐了：

- **Wolvesville** —— Steam 上不存在
- **Sonder** —— 无法验证为现存的免费合作游戏

该轮得分 50，与第 2 轮并列最低。失分主要来自 30 分的"可验证性"维度。

当前 prompt 中已三次以大写强调不得编造：

```
Do NOT recommend any games from your own knowledge that are not in this list.
Do NOT invent or hallucinate game titles.
You MUST select exactly 5 games, no more and no less.
```

**需要以自然语言反复恳求模型遵守的约束，说明约束本身没有被强制。**

### 1.3 解释未与检索证据关联

课程评审的批评之一：

> "Generated explanations being generic or not grounded in retrieved evidence."

当前 prompt 仅要求"解释为何契合"，未要求模型指出依据来自哪条标签、哪句评论或哪个评分。

### 1.4 技术前提已验证

本项目所用 `ollama` 版本的 `generate(format=...)` 接受 `dict[str, Any]`，即支持传入 JSON Schema 进行受约束解码，而非仅支持 `'json'` 字符串模式。

## 2. 目标与非目标

### 2.1 目标

- **G1** 使实体幻觉在**机制上不可能**发生，而非降低其概率
- **G2** 以 `app_id` 替代游戏名进行结果关联，消除模糊匹配这一类失败
- **G3** 消除静默降级：任何降级路径都必须留下可观测的信号
- **G4** 要求每条推荐给出检索证据，并**测量**其被支持的比例
- **G5** 产出可写入报告的幻觉率指标

### 2.2 非目标

- **N1 不改变 API 响应结构**。`{matches, answer, meta}` 保持不变，前端无需改动
- **N2 不做证据的强制校验**。证据支持度仅作**测量**，不作为拒绝条件，理由见 §4.4
- **N3 不更换生成模型**。`phi4-mini` 保持不变
- **N4 不改动检索与排序**
- **N5 不引入重排**。C2 独立立项

## 3. 需求

| 编号 | 需求 | 理由 |
|---|---|---|
| **R1** | 以 JSON Schema 传入 `format`，约束模型输出 | 受约束解码使非法格式无法被生成，而非依赖 prompt 恳求 |
| **R2** | Schema 要求返回 `app_id` / `reason` / `evidence`，`minItems = maxItems = 5` | 数量由 schema 保证，不再靠 prompt 强调 |
| **R3** | 校验每个 `app_id` 是否属于候选集，非法项丢弃并计数 | 候选集外的条目在机制上无法呈现给用户 |
| **R4** | 结果顺序由 `recommendations` 数组顺序决定 | 取代前缀模糊匹配重排 |
| **R5** | `answer` 文本由结构化字段组装 | 保持 API 结构不变（N1） |
| **R6** | 非法 JSON 时以更低温度重试一次 | 小模型偶发失败，一次重试成本低 |
| **R7** | 重试仍失败或有效条目不足 5 条时降级，并在 `meta.generation_mode` 中标明 | 降级可以接受，静默降级不可接受（G3） |
| **R8** | 统计并输出：非法 app_id 数、重试次数、降级次数、证据支持率 | 幻觉率是本变更唯一可宣称接近零的指标 |

### 3.1 Schema 定义

```python
RECOMMENDATION_SCHEMA = {
    "type": "object",
    "properties": {
        "recommendations": {
            "type": "array",
            "minItems": DEFAULT_MATCH_COUNT,
            "maxItems": DEFAULT_MATCH_COUNT,
            "items": {
                "type": "object",
                "properties": {
                    "app_id":   {"type": "string"},
                    "reason":   {"type": "string"},
                    "evidence": {"type": "string"},
                },
                "required": ["app_id", "reason", "evidence"],
            },
        }
    },
    "required": ["recommendations"],
}
```

### 3.2 `meta.generation_mode` 取值

| 取值 | 含义 |
|---|---|
| `structured` | Schema 输出，5 条全部通过校验 |
| `structured-retry` | 首次失败，重试后成功 |
| `structured-partial` | 有效条目不足 5 条，以排序结果补足 |
| `fallback-ranking` | 生成完全失败，回退至按分数排序 + 模板文本 |

## 4. 设计决策

### 4.1 为何用 `app_id` 而非游戏名

**被否决的方案**：继续用游戏名，但改进匹配算法（如编辑距离、归一化后精确匹配）。

**否决理由**：游戏名是**连续值**——存在截断、大小写、副标题、特殊字符、系列续作等无穷变体，任何匹配算法都只是把失败概率降低而非消除。`app_id` 是**离散标识符**，"在候选集中"是一个可判定的布尔条件。这正是 G1 所要求的从概率性改善转为机制性保证。

### 4.2 为何用 Schema 约束而非在 prompt 中要求 JSON

**被否决的方案**：prompt 中写"请只输出 JSON 数组"，解析失败则重试。

**否决理由**：这与当前实现同属一类——**请求模型配合**。受约束解码在解码阶段屏蔽掉会使 JSON 非法的 token，格式正确性由算法保证而非由模型的服从性保证。现有 prompt 中三处大写强调，本身就是该方案已经失败的证据。

### 4.3 为何保留降级路径，但必须可观测

**被否决的方案**：生成失败即返回错误。

**否决理由**：`phi4-mini` 是 38 亿参数的小模型，schema 约束下仍可能产生语义无效的输出（如返回不在候选集的 app_id）。此时返回按分数排序的结果，对用户仍有价值。

**但静默降级不可接受**——当前实现正是因为静默回退，使解析失败长期未被发现。`meta.generation_mode` 让降级在 API 响应中可见，评测时可统计其发生率。

### 4.4 为何证据只测量、不强制

**被否决的方案**：校验 `evidence` 是否真实存在于该游戏的标签或评论中，不通过则丢弃该条推荐。

**否决理由**：

1. 证据是模型改写后的自然语言，与原文并非字面一致，字面校验会大量误杀
2. 以小模型的能力，强制校验可能导致有效条目不足 5 条，频繁触发降级
3. 报告需要的是"证据支持率"这一**数字**，而非一个更严格的过滤器

采用词元重叠作为**近似度量**：证据文本与该游戏的标签、评分、评论摘要的重叠比例。作为指标报告，不作为拒绝条件。

### 4.5 为何不同时引入重排

C2（Cross-encoder 重排）会改变候选集的顺序，与本变更的效果混淆。且 C2 的依赖风险（Intel Mac 上的 PyTorch/ONNX）尚未验证。保持本次变更单一。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| `phi4-mini` 在 schema 约束下不稳定 | 频繁降级，改进无从体现 | 第 0 步先验证；不达 80% 则重估方案 |
| 受约束解码显著增加延迟 | 交互体验下降 | 第 0 步同时测量延迟 |
| 模型返回格式正确但 app_id 编造 | schema 无法防范语义错误 | R3 的候选集校验正是针对此项 |
| 组装出的 `answer` 文本不如自由文本流畅 | 表述质量下降 | 从 `reason` 字段组装，保留模型原话 |
| 降级发生率过高 | 实际效果接近未改动 | R8 统计降级次数，作为验收依据 |

## 11. 第 0 步验证结果

20 条真实查询（取自 `eval/queries_topical.jsonl`），`phi4-mini` + JSON Schema 受约束解码。

| 指标 | 结果 |
|---|---|
| 合法 JSON | **20/20 (100%)** —— 阈值 80% |
| 恰好 5 条 | 20/20 (100%) |
| 三字段齐全 | 20/20 (100%) |
| **候选集外 app_id** | **0** |
| 延迟 | 中位 106.2s，区间 82.3–138.3s |

明细见 `eval/spike/schema_spike_results.jsonl`。

### 11.1 结论

小模型在 schema 约束下的稳定性**显著优于预期**。PRD 起草时将此列为最大未知数，
并预设了"不达 80% 则重估方案"的退出条件；实测 100%，一次重试都未触发。

这与 §4.2 的论证一致：**受约束解码把格式正确性从"模型的服从性"转移到了"解码算法"**，
因此模型规模在这一维度上不再是瓶颈。

### 11.2 关于 A7 的正确解读

A7 实测幻觉为 0，但**这是结果，不是保证**。

它只说明模型在这 20 条查询上没有编造 app_id。**真正的机制保证来自 R3 的候选集校验**——
即使模型编造，校验也会拦下，这一点由 A2 的构造测试验证（返回 `999999` 与 `abc` 时被丢弃并计数）。

报告中应表述为"实体幻觉在机制上不可能"，依据是 A2 而非 A7。

### 11.3 延迟观察（非本 PRD 范围）

单次查询中位 106 秒，其中包含一次独立的 query expansion LLM 调用。
实测该调用一次输出 19 个关键词组，本身占用可观时间。

`OPTIMIZED_DESIGN.md` §6.2 指出该步骤可由 C4（tool calling）合并——模型在生成
`semantic_query` 时一并完成扩展，可省去一次 LLM 往返。这为 C4 的优先级提供了实测依据，
但不属于本 PRD 的范围。
